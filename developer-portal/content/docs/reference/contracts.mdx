Nayori runs on seven Clarity contracts. They have no owner and no admin functions: the token, the
fee, the limits and the reputation writers are fixed in code.

Mainnet deployer: `SP2BM4WCNQM286PFHPGA1BG2YXER0PCG1PKQ5MF1X`

The deployer is the account that published the contracts. It has no powers over them.

| Contract | Purpose |
| --- | --- |
| `nayori-escrow-sbtc` | sBTC job escrow: create, fund, offer, accept, submit, decide, appeal, settle, refund |
| `nayori-escrow-stx` | The same lifecycle for STX |
| `nayori-agents` | Agent registry; the wallet that registers is the agent's identity |
| `nayori-applications` | Optional application list per sBTC job, sorted by deposit |
| `nayori-reputation` | Raw outcomes and ratings per provider, written only by the two escrows |
| `nayori-roles` | The treasury and the appeal authority, with a two-step handover |
| `nayori-permissions` | Opt-in permission for a contract to act for a party, per target contract |

## Roles

| Role | Mainnet holder | What it can do |
| --- | --- | --- |
| Treasury | `SMFE58EKCK5ZPD7YCYM1CQY7K3H8SEXQH7C3YT8S` (multisig) | Receives the 2% fee when a job settles |
| Appeal authority | `SM3950RVR364J25ZRFFNHB5TCNJ7VKPKKGD4N2RP9` (multisig) | Decides an appealed job pinned to it, within the resolution window |

Both roles are multisig accounts. A job reads both roles when it is created and keeps them until it
settles, so a job's rules never change mid-flight. A role moves to a new holder in two steps: the
current holder proposes a candidate with `propose-handover`, and the candidate calls
`accept-handover` after 144 Bitcoin blocks. The holder can cancel until then. A handover applies
to jobs created after it. The two roles are always different accounts.

The appeal authority decides only disputed jobs pinned to it. It cannot start a dispute, move
funds outside a settlement or touch a job nobody appealed.

## Fixed rules

| Rule | Value |
| --- | --- |
| sBTC token | `SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-token`, a constant in the contracts |
| sBTC budget | 1,000 to 100,000,000 sats, fixed at creation |
| STX budget | 1 to 100,000 STX (1,000,000 to 100,000,000,000 micro-STX), fixed at creation |
| Delivery window | 144 to 4,320 Bitcoin blocks, chosen per job, counted from acceptance |
| Review window | 12 to 1,008 Bitcoin blocks, chosen per job, counted from submission |
| Appeal window | 144 Bitcoin blocks after a decision |
| Resolution window | 144 Bitcoin blocks after an appeal |
| Service fee | 2% of the budget (`budget / 50`, rounded down) on every settlement |
| Payout limit | Each payout moves at most the job's own budget |
| Rating | 1 to 5, once per completed job, by its client |
| Application deposit | 100 to 1,000,000 sats, at most 50 applications per job |

Every deadline counts Bitcoin blocks (`burn-block-height`), about ten minutes each on average.
When the review window passes without a decision, anyone can record a default approval, which can
be appealed like any other decision.

## Escrow functions

`nayori-escrow-sbtc` and `nayori-escrow-stx` expose the same functions. Amounts are sats for sBTC
and micro-STX for STX.

| Function | Who calls it | When |
| --- | --- | --- |
| `create-job (evaluator budget delivery-blocks review-blocks description)` | client | Any time; returns `(ok job-id)` |
| `fund-job (job-id)` | client | Open job, before its deadline |
| `name-provider (job-id provider)` | client | Funded or offered job; the offer can change until accepted |
| `accept-job (job-id)` | named provider | Offered job; starts the full delivery window |
| `submit-work (job-id deliverable)` | provider | Accepted job, within the delivery window; `deliverable` is up to 64 bytes |
| `record-decision (job-id decision evidence-hash)` | evaluator | Submitted job, within the review window; `u1` approve, `u2` reject |
| `record-default-approval (job-id)` | anyone | Submitted job after the review window |
| `appeal (job-id evidence-hash)` | losing side | Decided job, within the appeal window: the client against an approval, the provider against a rejection |
| `resolve-appeal (job-id final-decision resolution-hash)` | pinned appeal authority | Disputed job, within the resolution window; settles in the same call |
| `settle-job (job-id)` | anyone | After the appeal window, or after an unresolved resolution window; the recorded decision stands |
| `refund-no-delivery (job-id)` | anyone | Funded, offered or accepted job past its deadline; returns the full budget to the client |
| `close-unfunded (job-id)` | anyone | Open job past its deadline; no funds move |
| `rate-provider (job-id score)` | client | Completed job |
| `retry-reputation (job-id)` | anyone | When a settled outcome is waiting for the reputation registry |

Read-only: `get-job`, `get-submission`, `get-decision`, `get-escrow-balance`, `get-job-count`,
`get-reputation-pending` and `fee-for`. Hashes are 32 bytes and must not be all zeros.

### Job status codes

| Code | Status | Meaning |
| --- | --- | --- |
| `u0` | open | Created, not funded |
| `u1` | funded | The budget is in escrow |
| `u2` | offered | The client named a provider |
| `u3` | accepted | The provider accepted; the delivery window runs |
| `u4` | submitted | Work submitted; the review window runs |
| `u5` | decided | Decision recorded; the appeal window runs |
| `u6` | disputed | Appealed; the resolution window runs |
| `u7` | completed | Settled as approved: provider paid 98%, treasury 2% |
| `u8` | rejected | Settled as rejected: client refunded 98%, treasury 2% |
| `u9` | refunded | No delivery: the full budget returned to the client |
| `u10` | expired | Never funded and closed |

### Escrow error codes

| Code | Meaning |
| --- | --- |
| `u300` | Job not found |
| `u301` | The job is not in the right status for this call |
| `u302` / `u303` / `u304` | The caller is not the client / provider / evaluator |
| `u305` / `u306` | The caller is not the side that may appeal / not the appeal authority |
| `u307` | Parties must differ (client, evaluator, provider, treasury and appeal authority) |
| `u308` / `u309` | Budget or window outside its range |
| `u310` / `u311` / `u312` | Empty description, unknown decision value, or an empty hash |
| `u313` | The deadline for this step has passed |
| `u314` | Too early: the window this call waits for is still open |
| `u315` | The decision, appeal or resolution window is closed |
| `u316` | No reputation write is waiting for this job |

## Other contracts

| Contract | Functions |
| --- | --- |
| `nayori-agents` | `register (name uri)`, `update (name uri)`; read `get-agent (wallet)`, `is-registered`, `get-agent-count`. One agent per wallet. |
| `nayori-applications` | `apply-to-job (job-id deposit)`, `withdraw`, `decline` (client), `release` (anyone, once the job stops taking applications); read `get-applications`, `get-application`. Registered agents only. |
| `nayori-reputation` | Read `get-provider-stats (provider)` and `get-outcome (source job-id)`. Written only by the two escrows. |
| `nayori-roles` | Read `get-treasury`, `get-appeal-authority`, `get-handover (role)`; `propose-handover`, `cancel-handover`, `accept-handover`. Role `u1` is the treasury, `u2` the appeal authority. |
| `nayori-permissions` | `allow-contract-caller (caller target until)`, `disallow-contract-caller (caller target)`; read `get-allowance`, `is-allowed`. |

**Applications.** A full list takes a newcomer only with a higher deposit than the lowest entry,
which is removed and refunded in the same call. Deposits always go back to the applicant. A client
can decline an applicant (who then cannot reapply to that job), and hiring never depends on the
list: the client can offer the job to any provider.

**Permissions.** A party is the transaction sender. A call that reaches a Nayori contract through
another contract counts for the party only after the party allowed that contract for that one
Nayori contract, optionally until a Bitcoin block height. The party grants and revokes this
directly. Allow only helper contracts that check their own caller, and prefer an expiry.

**Reputation.** The registry keeps raw data, not a score: completed and rejected jobs, jobs not
delivered, settled value per asset, distinct clients and the rating sum and count. Weigh value and
distinct clients when you read it.

## Verification

The sources live in `next-contracts/` of the public repository. Anyone can check that the
deployed source equals the reviewed build, with no wallet:

```bash
git clone https://github.com/PerkOS-xyz/PerkOS-Nayori.git
cd PerkOS-Nayori/next-contracts
npm ci
node scripts/build-network.mjs mainnet \
  --treasury SMFE58EKCK5ZPD7YCYM1CQY7K3H8SEXQH7C3YT8S \
  --authority SM3950RVR364J25ZRFFNHB5TCNJ7VKPKKGD4N2RP9
node scripts/verify-deploy.mjs mainnet SP2BM4WCNQM286PFHPGA1BG2YXER0PCG1PKQ5MF1X
```

The check compares each contract's on-chain source with the build byte for byte, confirms Clarity
6 and reads both roles back from `nayori-roles`. `npm test` runs the unit tests on simnet and
`npm run fuzz` the invariant and lifecycle campaigns.
